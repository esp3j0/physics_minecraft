## 1. 背景与目标

到 REQ-008 为止,基础设施已经齐了:分片、迁移、回放、实体权威、激活票据、图形冒烟。但世界里的物理只有一种:
实体被生成、被推、落地、凝固成方块。**地形本身打不坏**——爆炸只推醒着的实体,方块纹丝不动。这是项目
README 所说"原版没有的物理"(结构坍塌等)的第一步。

本 REQ 的目标(v1):

1. **爆炸破坏地形**:爆心附近的方块按材料强度被破坏;外层的碎块脱落成实体飞出去,内层的直接粉碎;
2. **撞击破坏地形**:高速撞上地形的实体能撞掉方块(D1 决定是否纳入 v1);
3. **结构坍塌**:方块被移除后,与"地基"不再连通的悬空方块群塌落成实体;沙子这类松散材料下面一空就落;
4. **基岩**:世界最底层不可破坏,不会被炸穿进虚空(D6);
5. 全部满足既有的确定性、跨分片一致、回放等价约束;用图形冒烟验证画面。

不做挖掘机、不做持续受力的损伤累积、不做有限元应力分析(§11)。

## 3. 材料(D1、D6)

### 3.1 材料属性

`BlockRegistry` 追加材料查询(注册表数据,不是配置):

| 属性 | 含义 |
| --- | --- |
| `resistance` R | 抗爆强度,与爆炸压力同单位;`∞` = 不可破坏 |
| `impact_threshold` I | 撞击破坏所需的单格冲量,单位 kg·m/s(N·s);`∞` = 撞不坏 |
| `support` | `Connected`:与地基连通即不落(石、土);`NeedsBelow`:正下方不是实心就落(沙);`Anchor`:本身就是地基(基岩) |
| `pulverize_factor` k | 爆炸压力 > k·R 时粉碎,R < 压力 ≤ k·R 时脱落 |

### 3.2 内置方块表(ID 只追加)

| ID | 名称 | R | I(kg·m/s) | support | 说明 |
| --- | --- | --- | --- | --- | --- |
| 0 | air | — | — | — | 不变 |
| 1 | stone | 6 | 18 | Connected | 不变;默认实体的 `desc.block` 仍为 stone |
| 2 | dirt | 2 | 7 | Connected | 不变 |
| 3 | **bedrock** | ∞ | ∞ | Anchor | 新增 |
| 4 | **sand** | 2 | 4 | NeedsBelow | 新增 |

所有材料 `k = 2`。用 `SimpleRegistry::register` 注册、没有指定材料的实心方块(测试用的自定义方块表)
默认**不可破坏**(R、I 均为 ∞,`Connected`),既有用例行为不变。数值依据(demo,§12):`power 12, radius 8` 在 dirt 地面上破坏 60 格(粉碎 36、脱落 24);
1 格厚石墙被炸穿 8 格、墙后 0 格;3 格厚石墙只掉朝爆心一面(8 格);8 层静载每拍 1.31,远低于各阈值的
1/3;1 kg 方块约 6.8 m/s 撞坏 dirt、约 17.8 m/s 撞坏 stone,1 m 落地(4.4)撞不坏 dirt。

### 3.3 世界底层(D6)

超平坦 `classic` 最底层(y = −64)由 stone 改为 bedrock。高度不变,碰撞几何不变(两者都是实心),
既有轨迹类基线不受影响;断言层内容的单测随之更新(§9)。

## 4. 爆炸破坏(D2、D3)

### 4.1 求值位置与时机

- `Detonate` 本来就广播给所有扩张区覆盖爆炸范围的分片(REQ-001 §4.2)。每个分片在应用它时(`apply_prefix`,
  先按现状对实体施加冲量,再求值地形),**只对本体区内、所在 chunk 已装载的格**求值(owner 求值,不碰副本格);
  副本格由 owner 的 `Emergent` BlockWrite 在 N+1 同步;被破坏的格当拍写 air、重建所在 chunk 的 collider,
  并按 REQ-007 §4.11 触发地形变更唤醒;
- 求值是纯体素函数(`physics_sim::destruction::evaluate_blast`;输入:爆炸参数 + 本分片体素 + 材料表),
  不经 rapier;结果按 `BlockPos` 升序;
- **半径上限**:地形求值的有效半径 `r = min(radius, 16 m)`(16 m = REQ-001 的 `INTERACTION_MARGIN` 默认值)。
  这样爆心到本体区内任一受影响格的线段一定落在"本体区 ∪ 扩张区"之内,射线不会读到看不见的地方;
  实体冲量仍按原半径(REQ-001 §4.2 不变);
- **未装载的格**:不求值;射线穿过时不衰减(按空气处理)。

### 4.2 压力模型(D2)

- 基础压力 `P0(c) = power · (1 − d/r)`,`d` = 爆心到格 `c` 中心的距离,`d ≥ r` 不受影响(与实体冲量同一衰减);
- **推荐:射线衰减**(Minecraft 式):从爆心到格中心的线段上,每穿过一个实心格,压力减去该格的
  `R × attenuation`;墙能挡住身后的东西,厚墙只被炸掉朝爆心的一面;
- 备选:纯球形(不衰减),实现最简单,但一面墙挡不住任何东西,厚地基会被一次炸穿。

格 `c` 的有效压力记为 `P(c)`。`P(c) > R(c)` 即破坏。

**射线细则**(单元 02 定稿,与 demo 逐数一致):全程 f64;`d` 为爆心到格中心的欧氏距离;射线 = 从爆心到格中心的
体素遍历(Amanatides–Woo),**含起点所在格、不含目标格自身**;同时跨越多个面时按 x、y、z 的顺序逐轴步进,
中间格都计入;某轴方向分量为 0 时该轴不步进。

### 4.3 破坏后的去向(D3)

- `P(c) > k · R(c)`:**粉碎**,写 air,不产生实体;
- `R(c) < P(c) ≤ k · R(c)`:**脱落**,写 air,并在 N+1 生成一个实体:位于格中心,半边长 `DEBRIS_HALF_SIZE = 0.45`,
  `desc.block` = 原方块(落地后凝固回同种材料);初速度等价于对它施加冲量 `P(c) · dir'`(与实体的爆炸冲量同一定律),
  `dir' = normalize(0.4·u_x, 1, 0.4·u_z)`,`u` 为爆心指向格中心的单位向量——**以向上为主**:
  坑内的格四周是坑壁,水平速度只会把碎块顶在坑壁上(地形摩擦把竖直速度一起吃掉),向下的速度则把碎块压进坑底
  (demo 实测按爆心方向发射时碎块全部原地卡住);
- 脱落的格按定义是"刚好被炸松"的格(`P ≤ k·R`),所以碎块速度天生不高(dirt 2–4 m/s):小爆炸的效果是
  中心粉碎成坑、坑边松动的块翻起后落在坑里,而不是碎块四散飞远;
- **上限**:单次爆炸在单个分片内最多脱落 `max_debris_per_explosion` 个,按 `P(c)` 降序(同值 `BlockPos` 升序)
  取前者,其余改为粉碎;另受 §7 的每拍总上限约束。

### 4.4 与既有规则的关系

- 冻结体仍对爆炸免疫(REQ-001 §9.12);但它脚下的格若被炸掉,REQ-007 §4.11 会在下一拍唤醒它;
- 脱落实体是普通瞬态体:自动获得瞬态运动票、会凝固、会被强制落地、掉出世界会被虚空移除。

## 5. 撞击破坏(D1 决定是否纳入 v1)

- 物理步进后,从 rapier 接触对中取"醒着的实体 ↔ 地形复合体"的接触点;接触点沿法向退入地形一侧
  (退过薄片半厚)得到被撞的格;同一格取各接触点冲量的最大值;
- **冲量来源先做 spike**(撞击单元开工的第一步):demo 实测 Python 绑定读不到地形复合体接触点的冲量(恒为 0,
  原始形状之间正常)。先在 Rust 侧验证能否直接读到;读不到则用**动量差分** `I = m·Δv − m·g·dt`
  (demo 验证与理论值零偏差),按接触点把它归到被撞的格(多个地形接触点时归给法向冲击最大的那个点);
  spike 结论回写本节;
- 冲量 ≥ `impact_threshold(c)` → 该格脱落(撞击视为 `k` 之内,只脱落、不粉碎),初速度沿撞击方向,大小由超出量决定;
- 只在本体区内的格上判定;每拍每分片最多 `max_impact_breaks_per_tick` 个;
- **静载不能撞坏**:静止叠放产生的支撑冲量(1 kg 约 0.16 / 拍,8 层约 1.31)低于各阈值的 1/3(demo 实测);
- 有一拍"撞墙"瑕疵(该步内撞击者已被当作撞上固定墙解算),与 REQ-007 §4.10.4 的补偿路径同性质,可接受。

## 6. 结构坍塌(D4)

### 6.1 触发与搜索

- **触发**:本拍内任何把实心格改为非实心的写入(爆炸、撞击、坍塌、`SetBlock`、BlockWrite 信封;凝固与强制落地只写入
  实心格,不触发),把被改格的 6 个实心邻居作为种子;
- **搜索**:从每个种子做 6 连通的**向下优先**搜索(优先队列,键 `(y, x, z)` 升序),遇到以下任一即判定"已锚定"
  并停止:
  1. `support = Anchor` 的格(bedrock),或 y = `WORLD_Y_MIN`;
  2. 进入本分片内存中没有的 chunk(保守:看不见的地方当作有地基);
  3. 单个种子的访问格数超过 `collapse_max_cells`(保守:搜索预算用完当作有地基);
- **锚定标记**:一次搜索判定锚定后,它访问过的格在本拍内都记为已锚定,后续种子碰到即停;判定悬空的连通块
  同样记下,不重复搜索。结果与遍历顺序无关(连通分量是集合);
- 向下优先的理由(demo):20 层厚地基上移除一格,BFS 要访问 6099 格才碰到地基,向下优先只要 104 格;
  悬空块两种搜索访问量相当;锚定标记让同一片地面的后续种子 1 格即停(5 个种子合计 30460 → 6103 格);
- 约束 `collapse_max_cells ≥ collapse_max_cluster`:悬空块大于搜索预算时会被误判为锚定(demo:预算 256 时
  400 格的平台不塌),这类块静默留在原地,只计遥测。

### 6.2 塌落

- 未锚定的连通块:若格数 ≤ `collapse_max_cluster`,**本体区内的每一格**写 air 并在 N+1 生成一个实体
  (半边长 `DEBRIS_HALF_SIZE`,`desc.block` = 原方块,初速度 0);格数超过上限的整块**留在原地**(v1 已知限制,计入遥测);
- `NeedsBelow` 材料(沙)另有局部规则:正下方不是实心 → 单独脱落,与连通性无关;
- 塌落产生的移除本身也是写入,会触发下一轮搜索(下一拍),连锁坍塌自然发生。

### 6.3 跨分片一致

- 每个 owner 只转换本体区内的格,**不会重复转换**;
- 一个悬空块横跨两个分片时,两边各自看到对方的移除要晚一拍(BlockWrite N+1),因此两半可能相差一拍开始下落,
  视觉上可忽略;
- 收到 BlockWrite 信封后的写入同样触发本分片的搜索,保证另一半不会因为"没看到"而永远悬空。

## 7. 脱落实体的生成、ID 与预算(D5)

- **ID**:由调度器统一分配。分片在 tick N 末把"脱落请求"(格、方块、初速度)放进 outbox;调度器按 canonical
  序(分片序、`BlockPos` 序)分配 `EntityId::from_parts(EMERGENT_ORIGIN, seq)`,盖章为 N+1 生效的
  `SpawnDynamic`;`EMERGENT_ORIGIN` 是保留的 origin 值,与服务端的 origin 0 不冲突;计数器进调度器快照;
- 格在 N 拍写 air,实体在 N+1 出现:一拍空档(1/60 s),压在上面的东西最多下沉几毫米;
- **每拍上限**:每分片每拍最多新生成 `max_detach_per_tick` 个实体(爆炸、撞击、坍塌合计);超出的爆炸碎块粉碎、
  超出的坍塌块推迟到下一拍(格已写 air 的不推迟,只有尚未转换的连通块推迟);
- 生成后受 REQ-007 预算约束:醒数超过 `max_awake_dynamic` 时按既有规则淘汰(瞬态体 → 强制落地)。

0. **`req009-materials`**(单元 01):用 `fill` 搭石柱、沙柱,用 `set_block` 放一块基岩 → `wait_until` 各格方块

**viewer 脚本追加动作**(REQ-008 词汇扩展):`fill = { from = [x,y,z], to = [x,y,z], block = "stone" }`。
`from`/`to` 是长方体的两个对角(顺序任意),展开为按 `BlockPos` 升序的一组 `SetBlock` 命令;单步上限 4096 格,
超出即解析错误。**每帧最多发出 64 条**(服务器每个分片的收件箱容量为每拍 256 条,一次全发会被拒),
最后一批发出的那一帧该步结束,后续瞬时步骤可在同一帧继续。命令发出不等于已生效,场景应接 `wait_until block`。

## 11. 非目标

- 挖掘机、工具与持续受力的损伤累积(IDEA-001 §3.2 的"磨碎");
- 有限元或载荷传播的结构分析(IDEA-001 §3.3:先用连通性,demo 比较后另议);
- 整块悬空结构作为一个复合刚体下落(D4 的方案 B,需要新实体形状,另立 REQ);
- 材料密度(实体质量仍按碰撞体体积 × 默认密度);
- 悬臂的力矩与倾覆:连通性判据下,只要还连着任何一处地基,结构就不塌(石桥炸掉一根柱子,桥面仍挂在另一根柱子上);
- 流体、火、方块掉落物品;
- 网络协议变更(新方块只是新的 `BlockId`,客户端只需新增颜色)。

## 14. 验收标准(草案,demo 后定稿)

- **AC-D1 材料表**:内置方块与材料属性;ID 稳定;bedrock 不可破坏。
- **AC-D2 爆炸求值纯函数**:给定体素与爆炸参数,破坏格集合、脱落/粉碎划分、上限截断与参考实现一致;
  射线衰减下墙后格不受影响;遍历顺序无关。
- **AC-D3 owner 求值与跨片等价**:两分片切开的世界与单分片世界,同一爆炸破坏的格集合相同;副本在 N+1 一致。
- **AC-D4 脱落实体**:N 拍写 air、N+1 生成;ID 来自调度器、单调不复用、跨 checkpoint 延续;`desc.block` 为原方块;
  半边长 0.45;初速度等于冲量 `P·dir'` 除以质量,`dir'` 以向上为主;自动获得瞬态运动票;落地凝固回原材料。
- **AC-D5 坍塌**:桥、悬臂、沙柱塌落;贴着 bedrock 或连着地基的不塌;未装载 chunk 与搜索预算视为锚定;
  超过 `collapse_max_cluster` 的留在原地并计数。
- **AC-D6 跨片坍塌**:横跨两分片的悬空块,两边各转换本体区内的格,无重复、无遗漏。
- **AC-D7 上限与降级**:单次爆炸脱落上限、每拍生成上限、坍塌推迟;超出后醒体预算按 REQ-007 淘汰。

- **AC-D9 与 REQ-007 的衔接**:冻结体脚下被炸空后下一拍被唤醒;脱落实体的票据、强制落地、虚空移除照常。
- **AC-D10 回放与 checkpoint v6**:回放等价;v5 档拒绝。
- **AC-D11 配置与遥测**:`[destruction]` 各键、校验、默认值;遥测计数。

## demo 记录(阶段 2 填写)

`demos/terrain-destruction/`(任务 00,GLM Coding Lite 套餐实施,[824b02d](https://github.com/esp3j0/physics_minecraft/commit/824b02d);
总架构师复跑核对,2026-10-26)。数字均来自脚本输出。

1. **占位值不成立**:原 stone R=10、dirt R=4 下,`power 12, radius 8` 用射线衰减只破坏 16 格,石墙一格不掉;
   改为 stone 6、dirt 2 后,三条设计意图全部满足(§3.2)。
2. **k 取 2 而不是 demo 推荐的 3**(总架构师裁定):碎块大多落回坑里(见第 3 条),k = 3 时 44 个脱落块会把
   60 格的坑填回大半,坑看不出来;k = 2 时粉碎 36、脱落 24,坑保持可见,实体数也减半。
3. **碎块方向**:按"爆心指向格中心"发射时,地表格的方向全部朝下,碎块原地卡死(最远 0.11 m)。总架构师追加实验
   (`scratchpad`,未入库):改用 `P` 作冲量大小并以向上为主(水平分量 × 0.4)后,碎块能翻起(最高 0.47 m)、
   约 2.7 s 静止、无穿地;即使速度放大到 3 倍、power 加到 48,碎块也基本落在坑内或坑缘——坑壁挡住了水平运动,
   且脱落格按定义只是"刚好被炸松"。于是 §4.3 改为向上为主,§10 场景 1 的期望从"碎块飞散"改为"坑内有碎块"。
4. **坍塌搜索**:8 个结构两种搜索都与连通分量真值一致;向下优先把厚地基上的锚定判定从 6099 格降到 104 格;
   锚定标记省掉后续种子的重复搜索;预算 ≥ 512 时全部判对;跨分片晚一拍模拟中,各拍转换的并集等于单世界结果,
   没有任何格被转换两次。
5. **碎块尺寸**:半边长 0.45 静止最快(35 拍;0.5 要 93 拍,原因是相邻碎块初始互相接触、落地时推挤);
   与坑壁薄片的初始重叠(0.025)不会把碎块弹飞(实测 0.01 m/s)。
6. **撞击冲量**:Python 绑定读不到地形复合体接触点的冲量(恒为 0),改用动量差分,与理论值零偏差;
   Rust 侧能否直读留给撞击单元的 spike(§5)。
7. **独柱悬臂**:石桥炸掉一根柱子后,桥面仍连着另一根柱子,按连通性判定为锚定,不塌——§10 场景 2 改为两根柱子都炸。
8. 复核时发现的 demo 瑕疵(不影响结论):README 1.3 把推荐配置下 1 格厚墙写成 0/0/0,实测是墙被炸穿 8 格、
   墙后 0 格;`common.exposed_faces` 用按位运算判断实心,不同材料相邻时会在两实心格之间多生成面片——这些面片
   被实心格包住、实体碰不到,demo 结论不受影响;Rust 的 `collider_build` 按 `is_solid` 判断,无此问题。
